# SetupEngine — спецификация бизнес-логики

Движок отвечает на один вопрос: **подтверждён ли HTF-сетап на младшем таймфрейме**.

Он не пытается «угадать» сетап по одному алерту. Каждый сигнал обновляет состояние, а сообщение уходит только на переходе фазы.

## Состояние

Хранится отдельно для каждого символа:

```
smc:setup:BTCUSDT
smc:setup:ETHUSDT
```

Внутри — POI и сетапы. Mongo для подтверждения не используется.

## Иерархия таймфреймов

| HTF POI | LTF подтверждения |
|---|---|
| 1w | 1d, 4h |
| 1d | 4h, 1h |
| 12h | 1h |
| 4h | 15m, 5m |
| 1h | 15m, 5m |
| 15m | 5m, 1m |

Если алерт пришёл без `{{interval}}`, сигнал не участвует в сетапах.

## Фазы сетапа

```
WAIT_ENTRY
    │ price entered HTF POI
    ▼
WAIT_BOS
    │ internal BOS против направления POI
    ▼
WAIT_CHOCH
    │ internal CHoCH по направлению POI
    ▼
CONFIRMED
```

В любой момент до подтверждения сетап может уйти в `INVALIDATED` или `EXPIRED`.

## Правила

### POI создан (`OB/Imbalance Created`)

- создаётся зона на HTF;
- для каждого LTF из иерархии создаётся сетап в `WAIT_ENTRY`;
- если цена уже внутри диапазона — сразу `WAIT_BOS` и сообщение «вход в зону».

### Вход в POI (`Entered / Within / Mitigated`)

- сигнал может прийти с любого ТФ: движок сам находит HTF-зону, в которую попала цена;
- проверяется, что цена действительно внутри диапазона (допуск 0.05%);
- T0 → T1 не больше 24 часов;
- сетапы переводятся в `WAIT_BOS`.

### BOS (`internal`, против направления POI)

- должен прийти на том же LTF, который указан в сетапе;
- переводит сетап в `WAIT_CHOCH`;
- BOS до входа игнорируется.

### CHoCH (`internal`, по направлению POI)

- требует, чтобы BOS уже был;
- T2 → T3 не меньше 15 минут;
- T1 → T3 не больше 4 часов;
- подтверждает сетап, остальные LTF этого POI помечаются как superseded;
- сообщение собирается из T0–T3, а не из текущего алерта.

### Инвалидация

- `EXIT` или `BROKE` POI на HTF;
- противоположный swing BOS/CHoCH на HTF или LTF;
- истечение окон;
- инвалидация скоупится по символу и не может быть вызвана алертом другого инструмента;
- после подтверждения инвалидация тоже отправляется.

### Качество

- `HIGH` — есть целевой imbalance или CHoCH+;
- `MEDIUM` — базовая последовательность без цели.

## Что специально не делает

- не подтверждает сетап по одному CHoCH;
- не смешивает символы;
- не использует зону, которая старше 24 часов или уже инвалидирована;
- не считает входом `BROKE` — это инвалидация;
- не отправляет сообщение об OB, пока цена не вошла в зону.

## Конформанс-тесты

`src/engine/setup-engine.test.ts`:

- A — корректная последовательность 4H → 15m;
- B — чужой символ не подтверждает;
- C — старая зона не подтверждает;
- D — нет входа/BOS — нет сетапа;
- E — 1m POI не подтверждается на 1D;
- F — инвалидированная зона не подтверждает;
- G — одиночный swing BOS — не сетап;
- H — подтверждение не зависит от Mongo;
- I — чужой символ не инвалидирует BTC;
- плюс окна времени и пост-подтверждённая инвалидация.

## Источник сигналов: важное ограничение текущего `smc.pine`

Текущий индикатор, с которым шёл проект, отдаёт только:

- `Internal Bullish/Bearish BOS formed`
- `Internal Bullish/Bearish CHoCH formed`
- `Bullish/Bearish BOS formed` (swing)
- `Bullish/Bearish CHoCH formed` (swing)
- `Price broke bullish/bearish internal OB` — это **инвалидация** OB, а не вход
- `Equal highs/lows detected`
- `Bullish/Bearish FVG formed`

В нём **нет** алертов:

- `OB/Imbalance Created`
- `OB/Imbalance Entered/Within`

Без T0 и T1 движок не может собрать последовательность. То есть сам бот готов, но для живых сетапов нужно либо:

1. добавить в Pine `alertcondition` на создание и вход в OB/Imbalance;
2. либо отправлять эти события из другого индикатора/скрипта.

Минимальный контракт сообщений:

```
Bullish OB Created | {{ticker}} | {{interval}} | {{close}}
Bullish OB Entered | {{ticker}} | {{interval}} | {{close}}
Internal Bearish BOS formed | {{ticker}} | {{interval}} | {{close}}
Internal Bullish CHoCH formed | {{ticker}} | {{interval}} | {{close}}
```

Для медвежьего сетапа — зеркально.
